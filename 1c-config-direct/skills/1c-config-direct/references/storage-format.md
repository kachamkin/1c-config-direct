## 1. Таблица Config и файлы

- Колонки: `FileName`, `Creation`, `Modified`, `Attributes`, `DataSize`, `BinaryData`, `PartNo`. Каждая строка —
  «файл», сжатый raw deflate. Записи больше 10 000 000 байт режутся на части по `PartNo`, а `DataSize` (полный размер)
  повторяется в каждой части, поэтому `SUM(DataSize)` завышает объем.
- Год в `Modified` сдвинут на 2000 (4026 = 2026), время локальное сервера 1С.
- Имена: `<uuid>` — описание объекта; `<uuid>.<суффикс>` — модуль, форма, макет, справка (`.1` — справка в base64 HTML);
  служебные: `root`, `version`, `versions`, `DynamicallyUpdated`.
- Динамическое обновление: `DynamicallyUpdated` = `{1,<число>,<guid1>,<guid2>,…}` в порядке применения. Каждое
  обновление пишет измененные файлы как `<имя>_dynupdate_<guid>` и свой `versions_dynupdate_<guid>`. Актуальна копия
  от последнего обновления, в котором файл менялся; `Source` в `v8cfg.py` подставляет их вместо базовых имен.

## 2. Корень и описание конфигурации

- `root` = `{2,<uuid файла описания>,<base64>}`, `version` = `{{216,0,{<совместимость>,0}}}`, где 80327 = 8.3.27.
- Описание конфигурации: в нем внутренний uuid объекта Configuration (`{1,0,<uuid>},"Имя",{синоним}`). Модули
  конфигурации лежат под этим внутренним uuid, а не под uuid файла из `root`.
- Объекты перечислены коллекциями `{<GUID класса>,N,uuid…}`; GUID классов — константы (`CLASS`).
- Описание объекта — скобочный текст. Имя: `{n,n,<uuid>},"Имя",{k,"ru","Синоним","uk","…"},"Комментарий"`. Свойства
  позиционные, без имен: у справочника Валюты `CodeLength=3, DescriptionLength=10` лежат как `…,3,1,10,…`; номер версии
  формата свой у класса (у справочника `{57,`).
- Формы и макеты — отдельные файлы, перечисленные в коллекциях объекта. GUID коллекции форм свой у каждого класса
  (`FORM_LISTS`), GUID макетов общий (`3daea016…`). Команды описаны внутри владельца, их модуль — `<uuid команды>.2`.

## 3. Модули

Суффикс файла модуля зависит от класса (`MODULE`):
- у справочника `.0` — модуль объекта, `.3` — менеджера; у документа `.0` и `.2`;
- у регистров сведений и накопления `.1` — набор записей, `.2` — менеджер;
- у ПВХ `.15` и `.16`;
- у плана счетов `.14` — модуль объекта, `.15` — менеджера; у регистра бухгалтерии `.6` — набор записей, `.7` —
  менеджер; у плана видов расчета `.0` и `.3`; у регистра расчета `.1` — набор записей, `.2` — менеджер; у критерия
  отбора `.0` — менеджер; у последовательности набор записей — `.0`;
- у конфигурации `.0` — обычное приложение, `.5` — внешнее соединение, `.6` — управляемое приложение, `.7` — сеанс.

Способы хранения:
- контейнер с записями `info` + `text` (+ `image`). `info` = `{3,1,…}` — текст есть; `{3,2,…}` — только образ
  (поставка без исходников); `{3,3,1,"<соль>",1000}` — текст зашифрован паролем, образ открыт;
- контейнер обычной формы `form` + `module`;
- управляемая форма — скобочный текст `{<версия 2/3/4>,{описание формы},"текст модуля",…}`, модуль — строка с `""`;
- старые модули — голый текст с BOM прямо в `.0` (так же лежат текстовые макеты; различить можно только по классу владельца).

Внутренний контейнер — классический: заголовок «первый свободный блок, размер страницы, ревизия, резерв», блоки
`\r\n<размер> <страница> <следующий> \r\n` по 8 hex-цифр. Если первый свободный блок не `7fffffff`, контейнер
переписывался на месте, и в свободных страницах остается старый текст.

## 4. Типы полей

Поле — блок `{…{3,{1,0,<uuid>},"Имя",{синоним},…},{"Pattern",тип1,тип2…}}`. Типы:
`{"B"}` булево; `{"S"}` строка без ограничения, `{"S",n,1}` переменной длины, `{"S",n,0}` фиксированной;
`{"N",d,f,0|1}` число (1 = неотрицательное); `{"D"}` дата и время, `{"D","D"}` дата, `{"D","T"}` время;
`{"#",uuid}` — все остальное:
- TypeId сгенерированного типа (`CatalogRef.X` и т.д.). Стоит на фиксированной позиции заголовка описания, своей
  для класса (`GEN_POS`): у справочника Ref — `(1,3)`, у перечисления `(1,1)`, у определяемого типа `(1,1)`, у ПВХ
  Characteristic — `(1,9)`;
- константа платформы (`PLATFORM`): ValueStorage, UUID, «любая ссылка» (`280f5f0e…`, в старых XML-форматах
  `cfg:AnyRef`, в новых `cfg:AnyIBRef`), «все ссылки класса» (`TypeSet:CatalogRef` …);
- в источниках подписок «все объекты класса» — сам GUID класса (`TypeSet:DocumentObject` …).

Тип значения ПВХ лежит в заголовке объекта (`root[1]`), не в блоке поля. Позиции типов для планов счетов,
регистров бухгалтерии и расчета и планов видов расчета сняты на УТП 1.2. У плана видов расчета все позиции
сдвинуты на 1 (Ref — `(1,4)`). Коллекции полей (`KIND`): `888744e1…` —
реквизиты ТЧ почти у всех классов; у регистра сведений `13134203` — измерения, `13134202` — ресурсы, `a2207540` —
реквизиты; у регистра накопления `b64d9a43`, `b64d9a41`, `b64d9a42`.

## 5. Форматы .cf и .cfe

- Классический .cf — контейнер с теми же файлами, что строки Config (проверено на УТ 3.1: 15 261 файл,
  все совпали после распаковки).
- Современный .cf (встречен при совместимости 8.3.17, 8.3.20, 8.3.23, 8.3.27; при 8.2.14–8.3.12 — классический):
  сначала маленький классический контейнер с заглушкой — «пустой конфигурацией» `BB71D8BD57664101889B95C34FEA2351` и
  одним языком, — а сразу за ним 64-битный контейнер с настоящей конфигурацией. Его заголовок: 8 байт `FF`,
  размер страницы, ревизия, резерв (20 байт); блоки `\r\n` + три поля по 16 hex-цифр; записи оглавления — 3 × uint64;
  адреса отсчитываются от начала 64-битного контейнера. Внутренние контейнеры модулей остаются классическими.
- .cfe (расширение) — классический контейнер, но вместо `root` и `version` одна запись `configinfo` =
  `{0,{216,0,{<совместимость>,0}}},{2,<uuid описания>,<base64>}`.
- Заимствованный объект расширения узнается по блоку имени: `{3,{1,0,<uuid>},"Имя",{синоним},"",1,N,<uuid>,2,<uuid
  объекта конфигурации>,…}`, у собственного объекта там `…,"",0,0,<нулевой uuid>,0}`. Сверено с XML
  (`ObjectBelonging Adopted`) на 25 объектах. Свойства заимствованного объекта в .cfe — значения по умолчанию (длина
  кода 9, наименования 25, номера 9), настоящие лежат только в основной конфигурации. Исключения: списки (владельцы,
  движения) в части объектов, которые есть в расширении, и тип заимствованной константы.

## 6. Что лежит рядом

- `ConfigSave` — сохраненная в конфигураторе, но не примененная к базе конфигурация. Скилл ее не накладывает
  (наложение не проверено: во всех локальных базах она была пустой).
- Расширения базы — в `ConfigCAS`: `FileName` = SHA-1 от сохраненных (сжатых) байт. `_ExtensionsInfo._ExtensionZippedInfo`
  содержит двоичный SHA-1 корневой записи расширения (формат как у `configinfo`). Дальше корня не разбиралось.
- Поставка (данные поддержки) — `<uuid файла описания>.<uuid>`: двойной deflate, внутри контейнер с конфигурацией
  поставщика (у УТ 3.1 — 15 210 файлов, 177 МБ). Ее можно открыть как источник, если сохранить распакованный контейнер в файл.
- `Params.DBNames` — соответствие объектов и таблиц СУБД (для чтения данных, этим скиллом не используется).

## 7. Как пополнить таблицы

Если в выводе `fields` встречается `Unknown:<uuid>`, а у модулей нет имени или вида, нужна XML-выгрузка той же
конфигурации. `check <папка>` покажет расхождения рядом с XML-именем типа, по ним понятно, что добавить в `PLATFORM`.
Позиции `GEN_POS` для нового класса ищутся так: TypeId из `<xr:GeneratedType>` в XML нужно найти в разобранном
описании объекта (`parse_brace`) и записать путь индексов. Суффиксы модулей нового класса определяются сравнением
текста `<uuid>.<суффикс>` с `.bsl` из XML.

## 8. Файловая база 1Cv8.1CD

Файл `1Cv8.1CD` — собственная страничная СУБД 1С. Таблицы `Config`, `ConfigSave`, `Params`, `Files` в ней те же, что
в SQL, только без `PartNo`: файл хранится одним BLOB целиком. Читает `scripts/onecd.py`, дальше разбор общий.
Проверено 26.11.2026 на 21 локальной файловой базе (все в формате 8.3.8, страница 8192). Модули и поля четырех из них
(УТП 1.2, BAS Розница, отраслевая конфигурация, БП Украины) сверены с XML на 100%.

- Страница 0 — заголовок: `1CDBMSV8`, версия формата `8.3.8.0`, число страниц (uint32), резерв (int32), размер
  страницы (uint32). Формат 8.2.14 (страница 4096, другие заголовки объектов) не реализован.
- Объект (файл внутри базы) — страница-заголовок: `1C FD`, fatlevel (int16), версия (3 × uint32), длина (uint64),
  номера страниц (uint32…). При fatlevel 0 это страницы данных, при fatlevel 1 — страницы FAT по pagesize/4 номеров.
  Страница 1 — объект свободных страниц (`1C FF`).
- Страница 2 — корневой объект. Это хранилище BLOB из блоков по 256 байт: следующий блок (uint32), занятая длина
  (uint16), 250 байт данных. Блок 0 — голова списка свободных блоков. Блок 1 — язык[32], число таблиц (int32),
  индексы BLOB с описаниями таблиц.
- Описание таблицы — однобайтный скобочный текст: `{"Config",0,{"Fields",{"FILENAME","NVC",0,128,0,"CS"},…},
  {"Indexes",…},{"Recordlock","0"},{"Files",<записи>,<BLOB>,<индекс>}}`. Имена таблиц в разных базах записаны
  по-разному (`Config` или `CONFIG`), поэтому искать надо без учета регистра.
- Запись фиксированной длины. Сначала байт «свободна», затем поле версии записи (тип RV, 16 байт), если оно есть, затем
  остальные поля по порядку описания. Размеры полей:
  - B — длина, L — 1 байт;
  - N — (длина + 2) / 2 байт BCD, DT — 7 байт BCD;
  - NC — длина × 2, NVC — 2 + длина × 2;
  - I и NT — 8 байт: индекс BLOB в объекте BLOB таблицы и длина.

  У поля, допускающего NULL, впереди байт-флаг.
- Расширения файловой базы лежат в `CONFIGCAS`, их имена — в таблице `_ExtensionsInfo` (поле `_EXTNAME`).

## 9. Свойства объектов и обучающий скрипт

Свойства объекта (периодичность, режим записи, иерархия, длины кода, проведение, основные формы и т.д.) лежат
позиционно в описании объекта. Позиции и коды значений хранятся в `scripts/props_tables.json` и сняты
`scripts/learn_props.py` сверкой с XML-выгрузками.

- **Версии формата.** Позиция зависит от класса и от версии формата описания объекта. Версия — первое число заголовка,
  `root[1][0]`: например, у справочников 22…57. В одной старой конфигурации их бывает до семи. Пример: «Иерархический»
  в версии 30 стоит на `(1,32)`, начиная с 45 — на `(1,37)`.
- **Ссылки на объекты метаданных** записаны во внутреннем формате значения `{"#",157fa490-4ce9-11d4-9415-008048da11f9,{1,<uuid>}}`.
  Список ссылок выглядит как `{0,N,ссылка…}` — так хранятся движения документа `(1,24)`, владельцы, «ввод на
  основании», состав подсистемы. Одиночная ссылка (основная форма, нумератор) — это uuid или такая же запись,
  нулевой uuid означает пустое значение.
- **Метод общего модуля** (обработчик подписки, метод регламентного задания) — uuid модуля и следующая за ним
  строка с именем процедуры. В таблице у такого свойства путь заканчивается на `-1`.
- **Коды значений** бывают такие:
  - число как есть (`codec: null`);
  - строка (`str`);
  - строка с английским кодом до подчеркивания (`prefix`): `"BeforeWrite_ПередЗаписью"` → `BeforeWrite`;
  - таблица до 12 кодов (`{"0": "Nonperiodical", …}`).
- **Как скрипт выбирает место:**
  - место голосуется группами «класс + версия», вес группы равен числу объектов;
  - своё место версия получает, только если в ней не меньше 8 объектов;
  - малые версии лишь подтверждают общее место, а где оно не подтвердилось, версия попадает в `refused_versions`
    и для нее ничего не подставляется;
  - свойство с ошибками больше 0,5% на объектах обучения в таблицу не попадает. Не попадает и таблица кодов,
    в которой на код меньше трех объектов, больше 12 кодов или значения не похожи на перечисление
    (латинский идентификатор или число): свободный текст — комментарии, адреса — в таблицу не попадает.
- **Точность.** 26–27.11.2026 таблица снята на семи конфигурациях:
  - всего 306 свойств; на объектах обучения верны 99,99% значений (неверны 15 из 166 тыс.);
  - на двух конфигурациях, которые в обучении не участвовали, верны 99,9%.

Пересобрать таблицу (при новых конфигурациях или платформе), источники и выгрузки — парами:

```
py -X utf8 learn_props.py sql:base1 "D:\Conf1" "D:\Bases\Shop\1Cv8.cf" "D:\Conf2" --samples cache.pkl --out props_tables.json
py -X utf8 learn_props.py --samples cache.pkl --out props_tables.json      # повторно, на сохраненных образцах
```

**Редкие свойства — `scripts/props_manual.json`.** Обучающему скрипту нужны объекты с разными значениями, а у части
классов объектов мало и значения одинаковые: все встреченные регистры бухгалтерии корреспондирующие, все регистры
расчета с базовым периодом, все номера процессов и задач строковые. Для них собрана тестовая конфигурация с нарочно
противоположными значениями (некорреспондирующий регистр, план счетов без субконто, числовые коды и номера, регистр
расчета без базового периода, длина порядка счета не равна длине кода). Ее делают скиллы 1c-skills: `cf-init`,
`meta-compile` по JSON, затем `db-create`, `db-load-xml`, `db-update`. Места найдены сверкой с ее XML-выгрузкой и
выгрузками клиентских конфигураций. Записи файла накладываются поверх `props_tables.json`, поэтому повторное обучение
их не стирает. Так же исправлена ошибка обучения: длину наименования ПВР скрипт привязал к месту длины кода с таблицей
перекодировки, которая на обучающих объектах случайно давала верный ответ.

## 10. Стандартные реквизиты

Код — `scripts/v8std.py`.

**Типы не хранятся.** Состав и типы стандартных реквизитов платформа выводит из свойств объекта (раздел 9), скрипт
повторяет ее правила. Правила сверены с тем, что сообщает платформа через COM (`Метаданные.<класс>[i].СтандартныеРеквизиты`
и `.СтандартныеТабличныеЧасти`, имя типа через `XMLТип`), на пяти базах: четыре клиентские (отраслевая, УТП 1.2,
BAS Бухгалтерия, BAS КУП) и тестовая из раздела 9. Совпали все 19 078 реквизитов; не видны только объекты расширений
базы, которые COM показывает, а таблица Config не содержит.
- Справочник и ПВХ: `ИмяПредопределенныхДанных` String(256), `Предопределенный`, `Ссылка`, `ПометкаУдаления`.
  - `ЭтоГруппа` — при иерархии групп и элементов (у ПВХ иерархия всегда такая), `Родитель` — при любой иерархии.
  - `Владелец` — ссылки на владельцев.
  - `Наименование` String(DescriptionLength) и `Код` — только при ненулевой длине. Код — String(CodeLength) с
    CodeAllowedLength или Number(CodeLength,0,Nonnegative); у ПВХ и плана обмена код всегда строка.
  - У ПВХ еще `ТипЗначения` (TypeDescription).
- Документ, бизнес-процесс, задача: `Ссылка`, `ПометкаУдаления`, `Дата` DateTime, `Номер` (как код).
  - У документа еще `Проведен`.
  - У бизнес-процесса — `Стартован`, `Завершен`, `ВедущаяЗадача` (TaskRef любой задачи конфигурации).
  - У задачи — `Наименование`, `Выполнена`; `БизнесПроцесс` и `ТочкаМаршрута` — по процессам, у которых она задача,
    и только если такие процессы есть.
- Перечисление: `Ссылка`, `Порядок` Number(0,0).
- План обмена: `Ссылка`, `ПометкаУдаления`, `Код`, `Наименование`, `ЭтотУзел`, `НомерОтправленного` и
  `НомерПринятого` Number(10,0,Nonnegative).
- Журнал документов: `Тип` (Type), `Ссылка` (DocumentRef его документов), `Дата`, `Проведен`, `ПометкаУдаления`.
  `Номер` — объединение типов номеров документов: строка длины самого длинного строкового номера (фиксированная, если
  у всех таких документов длина фиксированная) и (или) Number длины самого длинного числового.
- Регистр сведений:
  - `Период` — только у периодического: DateTime при Second и RecorderPosition, иначе Date;
  - у подчиненного регистратору — `Регистратор` (документы, в движениях которых он есть), `НомерСтроки`
    Number(9,0,Nonnegative), `Активность`;
  - у независимого непериодического стандартных реквизитов нет совсем.
- Регистр накопления: `Период` DateTime, `Регистратор`, `НомерСтроки`, `Активность`; `ВидДвижения`
  (AccumulationMovementType) — только у регистра остатков.
- План счетов: `ИмяПредопределенныхДанных`, `Порядок` String(OrderLength), `Забалансовый`, `Вид` (AccountType),
  `Наименование`, `Код` (всегда строка переменной длины), `Родитель`, `Предопределенный`, `ПометкаУдаления`, `Ссылка`.
  Стандартная табличная часть `ВидыСубконто` есть всегда: `ТолькоОбороты`, `Предопределенное`, `ВидСубконто`
  (ссылка на ПВХ видов субконто, без ПВХ — пустой тип), `НомерСтроки`.
- Регистр бухгалтерии: у некорреспондирующего `Счет` и `ВидДвижения` (AccountingMovementType), у корреспондирующего
  их нет; затем `Активность`, `НомерСтроки` Number(9,0), `Регистратор`, `Период` DateTime и пары `СубконтоK` (тип
  значения ПВХ видов субконто) + `ВидСубконтоK` для K от 1 до максимального числа субконто плана счетов.
- ПВР: `ИмяПредопределенныхДанных`, `Предопределенный`, `Ссылка`, `ПометкаУдаления`, `ПериодДействияБазовый` (при
  использовании периода действия), `Наименование`, `Код` (строка или число). Стандартные табличные части с реквизитами
  `Предопределенный`, `ВидРасчета`, `НомерСтроки`:
  - `ВедущиеВидыРасчета` — всегда, `ВидРасчета` — ссылка на любой ПВР конфигурации;
  - `ВытесняющиеВидыРасчета` — при использовании периода действия, ссылка на сам ПВР;
  - `БазовыеВидыРасчета` — при зависимости от видов расчета, ссылки на базовые ПВР.
- Регистр расчета: `ПериодРегистрации` DateTime, `Сторно`, `Активность`, при базовом периоде
  `БазовыйПериодКонец/Начало`, при периоде действия `ПериодДействияКонец/Начало` и `ПериодДействия` (все DateTime),
  `ВидРасчета` (ссылка на его ПВР), `НомерСтроки` Number(9,0), `Регистратор`. Периодичность на типы не влияет.
- Табличная часть любого класса: `НомерСтроки` Number(5,0,Nonnegative).

**Табличные части** — члены коллекции табличных частей своего класса в корне описания (`TS_COLL`: у справочника
`932159f9-…`, у документа `21c53e09-…` и т.д.). Узел выглядит как `{заголовок с именем, {коллекция реквизитов}}`. Так же
выглядят шаблоны URL HTTP-сервисов и операции веб-сервисов, поэтому коллекцию задает класс. Сверено с XML на семи
конфигурациях: 2877 табличных частей из 2877.

**Настройки**, измененные в конфигураторе, лежат списком
`{1,N,{-id},510405d3-2a0c-4fea-960a-7fee59b32f9b,{14,25,<GUID свойства>,<значение>,…},…}` рядом с заголовком объекта,
у табличной части — в ее заголовке. Если ничего не меняли, списка нет, и в XML-выгрузке тогда нет блока
`<StandardAttributes>`.
- id реквизита свой у каждого класса (`STD_IDS`). У справочника: `-2` Код, `-3` Наименование, `-4` Родитель,
  `-5` Владелец, `-6` ЭтоГруппа, `-7` ПометкаУдаления, `-8` Ссылка, `-10` Предопределенный,
  `-13` ИмяПредопределенныхДанных. У `НомерСтроки` табличной части — `-10`, у обработки и отчета — `-3`, у ПВР —
  `-100`. У `СубконтоK` регистра бухгалтерии id — пара `{K-1,91162600-3161-4326-89a0-4a7cecd5092a}`, у `ВидСубконтоK` —
  `{K-1,b3b48b29-d652-47ab-9d21-7e06768c31b5}`.
- Списки стандартных табличных частей лежат в заголовке объекта блоком `{0,N,<id части>,{…,<список>…},…}`, есть
  всегда: у плана счетов `-12` ВидыСубконто, у ПВР `-30` ведущие, `-20` вытесняющие, `-10` базовые виды расчета.
- Свойства по GUID (`STD_KEYS`):
  - `cf4abea3-…` синоним, `4690ff70-…` подсказка, `cf4abea4-…` комментарий, `f49e4ced-…` маска;
  - `2723eb98-…` проверка заполнения: перечисление `98ea8e5a-…`, 0 — не проверять, 1 — выдавать ошибку;
  - `2c8143d5-…` «заполнять из значения заполнения».
- Строка на языках — `{"#",87024738-fc2a-4436-ada1-df79d395c424,{N,"ru","…","uk","…"}}`. Переводы строк внутри
  бывают `\r\r\n`, XML-выгрузка пишет их одним LF.
- Сверено с XML на девяти клиентских конфигурациях и тестовой: 34 763 реквизита, у 4041 из них настройки
  менялись, расхождений нет.

**Пометка `(assumed)`** ставится реквизиту, свойство которого (длина кода, тип номера, корреспонденция…) прочитано с
места, общего для известных версий формата, а для версии этого объекта место не проверено (раздел 9).

## 11. Составные свойства: ввод по строке, поля блокировки, характеристики

Код — `scripts/v8comp.py`, места свойств в заголовке — `props_manual.json` (виды `fields` и `characteristics`).

- **Ссылка на поле** — `{"#",60ea359f-3a6e-48bb-8e71-d2a457572918,{<id>}}` для стандартного реквизита (id из
  раздела 10 для класса объекта, которому принадлежит поле) или `{…,{0,<uuid поля>}}` для реквизита, измерения,
  ресурса. В характеристике то же тело приходит как `{1,{<id>}|{0,<uuid>},0}`, а `{-1}` значит «не задано».
  `Ссылка` табличной части — id `Ссылки` ее владельца (у справочника `-8`).
- **Ввод по строке и поля блокировки данных** — `{1,{0,N,<ссылка на поле>…}}`. Места, например: у справочника версий
  45–57 ввод по строке — `(1,42)`, у версии 30 — `(1,36)`; поля блокировки — `(1,54)`; у документа `(1,29)` и
  `(1,47)`.
- **Характеристики** — `{1,{N,<характеристика>…}}`, у справочника на `(1,52)`, у документа на `(1,45)`, у ПВХ на
  `(1,50)`, у ПВР на `(1,54)`. Характеристика — `{"#",fe839d42-d094-40ba-b903-75bccc21ba30,{4,…}}`; после версии `4`
  идут:
  1. `{1,<uuid>}` — откуда берутся виды (табличная часть, справочник, ПВХ);
  2. `{1,<uuid>}` — где хранятся значения (табличная часть, регистр сведений);
  3. поля значений: объект, вид, значение;
  4. поле отбора видов и значение отбора: `{"#",5c14e26f-099b-4d37-84a6-b433d87400da,{0,<TypeId>,<uuid элемента>}}` —
     предопределенный элемент, `{"S","…"}` — строка;
  5. ключевое поле видов;
  6. четыре необязательных поля: путь к данным, использование и ключ нескольких значений, порядок. Ни в одной из
     выгрузок они не заполнены, поэтому их порядок не проверен.
- **Предопределенные элементы** лежат в `<uuid объекта>.1c`: элемент — `{"#",<TypeId>,{1,<uuid>}},{"B",<группа>},
  {"#",<TypeId>,{1,<родитель>}},{"S","<имя>"},…`. Ссылку на удаленный элемент XML-выгрузка пишет как
  `<TypeId>.<uuid>`, скилл так же.
- **Как найдены места:** каждый элемент заголовка разбирался как список полей и как список характеристик, и
  результат сравнивался с XML девяти клиентских конфигураций и тестовой. Ввод по строке нашелся у 3270 объектов,
  поля блокировки — у 73, характеристики — у 723.
