# Конфигурация 1С напрямую из SQL, файловой базы или .cf

Скилл читает то, что лежит в хранилище конфигурации, и ничего не меняет. Из базы он только выбирает строки (SELECT).
Конфигуратор не нужен, лицензия не нужна, база не блокируется.

Проверено 26–27.11.2026 командой `check` на девяти разных конфигурациях с готовыми XML-выгрузками; источники — SQL,
.cf и файловые базы:
- УТ 2.3 с обычными формами;
- УТ 3.1;
- УТП 1.2 с планами счетов и расчетом;
- BAS Розница;
- BAS Бухгалтерия 2.1;
- BAS КУП 2.5;
- ITIL Рарус;
- отраслевая конфигурация стороннего разработчика;
- Бухгалтерия для Украины 1.2.

Тексты всех 30 267 непустых модулей совпали с XML байт в байт, типы 117 174 полей тоже совпали. Единственное
отличие — висячая ссылка на удаленный объект, которую XML-выгрузка выбрасывает. Еще шесть клиентских .cf, два .cfe и
файловая база на 9,7 ГБ читаются без ошибок.

Стандартные реквизиты проверены 27.11.2026:
- состав и типы сверены с тем, что сообщает сама платформа через COM, на пяти базах: четыре клиентские (отраслевая,
  УТП 1.2, BAS Бухгалтерия, BAS КУП) и тестовая конфигурация с нарочно редкими значениями свойств
  (некорреспондирующий регистр бухгалтерии, числовые коды и номера, регистр расчета без базового периода). Совпали
  все 19 078 реквизитов;
- настройки (синонимы, подсказки, проверка заполнения) сверены с XML на тех же девяти конфигурациях и тестовой:
  совпали у всех 34 763 реквизитов, из них у 4041 настройки менялись.

Три клиентских .cfe сверены с XML-выгрузками этих расширений: модули, поля, свойства и стандартные реквизиты совпали.

## Запуск

Скрипты лежат в папке `scripts` рядом с этим файлом (папка скилла указана в начале при загрузке; ниже это `<скилл>`).
Запускай через Bash, так кириллица в выводе не портится:

```bash
py -X utf8 "<скилл>/scripts/cfgread.py" [--no-sync] [--cache <папка>] <источник> <команда> [параметры]
```

Если `py` нет, подойдет `python`/`python3` (Python 3.8+, сторонние пакеты не нужны). В PowerShell перед запуском выполни
`[Console]::OutputEncoding = [Text.Encoding]::UTF8`. Служебные строки (синхронизация, время, итоги) идут в stderr
с `#`; когда нужен только текст модуля, добавь `2>/dev/null`.

### Источник

| Источник | Что это |
|---|---|
| `sql:<база>` или `sql:<сервер>/<база>` | таблица `dbo.Config` базы MS SQL; сервер по умолчанию `.`, вход по Windows-учетной записи |
| `C:\путь\файл.cf`, `файл.cfe` | файл конфигурации или расширения |
| `C:\путь\1Cv8.1CD` или папка файловой базы | таблица Config файловой базы, читается прямо из файла, без кеша |
| папка | уже выгруженные строки Config, по файлу на запись (так устроен кеш) |

Имя базы — это имя БД в SQL Server (обычно совпадает с именем ИБ в кластере; список —
`sqlcmd -S . -E -Q "SELECT name FROM sys.databases"`).

**Кеш для SQL.** Строки складываются в `%LOCALAPPDATA%\1c-config-direct\<сервер>__<база>\Config`, для сервера `.` —
`local__<база>`. Другую папку задает `--cache <папка>` или переменная `CFGREAD_CACHE`. Каждый запуск без `--no-sync`
докачивает только записи с изменившимися `Modified`/размером и переписывает `_manifest.tsv` и `_info.tsv`. Первое чтение
УТ 3.1 идет около 25 с, повторное около 3 с. С `--no-sync` кеш берется как есть и ничего не пишется; так удобно задавать
серию вопросов подряд. В кеше лежат копии конфигураций клиентов, по просьбе пользователя его можно удалить целиком.

## Команды

| Команда | Что делает |
|---|---|
| `info` | имя, синоним, поставщик и версия, совместимость, формат файла, динамические обновления, ConfigSave и расширения базы (для SQL), объекты по классам, модули: по способам хранения, без текста, пустые |
| `objects [фильтр] [--all]` | объекты с синонимами; `--all` добавляет формы, команды, макеты |
| `modules [фильтр] [--no-text]` | модули: полное имя, способ хранения, длина текста (`-` — текста нет); `--no-text` — только модули без текста |
| `module <имя> [-n] [--lines A-B] [--all]` | текст модуля; `-n` нумерует строки, `--lines 250-280` выводит диапазон (с номерами) |
| `grep <текст> [--re] [-i] [--path фильтр] [--ctx N] [--proc] [--files] [--max N]` | поиск по модулям: `имя:строка: текст`, контекст `имя-строка-`, группы через `--`; `--proc` добавляет процедуру, в которой стоит совпадение; `--max` по умолчанию 500 строк |
| `fields [фильтр] [--no-standard]` | реквизиты, реквизиты ТЧ, измерения, ресурсы, константы, параметры сеанса, определяемые типы, источники подписок — с типами; первыми идут стандартные реквизиты (Ссылка, Код, Наименование, Владелец, Родитель, Дата, Номер, Период, Регистратор, НомерСтроки…), `--no-standard` их убирает |
| `props [фильтр] [--prop имя] [--all]` | свойства объектов: периодичность, режим записи, иерархия, владельцы, движения, ввод на основании, ввод по строке, поля блокировки данных, характеристики, основные формы, флаги общих модулей, обработчики подписок и т.д.; `--prop` — одно свойство по многим объектам, `--all` — и пустые |
| `usedby <объект> [--types]` | обратные ссылки: где объект указан в свойствах других — какие документы пишут в регистр, в каких подсистемах объект, какие подписки и задания вызывают модуль; `--types` — еще и реквизиты этого типа |
| `export <папка> [--path фильтр] [--no-fields]` | модули в раскладке XML-выгрузки (`Catalogs/X/Ext/ObjectModule.bsl`, `…/Forms/Y/Ext/Form/Module.bsl`) плюс `objects.tsv`, `props.tsv` и `fields.tsv` (в нем и стандартные реквизиты, вид `Standard`, без uuid) |
| `diff <источник2> [--path фильтр] [--show имя\|*] [--fields] [--props]` | сравнение: модули только в A / только в B / измененные (+/− строк); `--show` — unified diff; `--fields` — поля, которые появились, пропали или сменили тип, включая стандартные (длина кода, состав регистраторов); `--props` — изменившиеся свойства |
| `check <папка XML-выгрузки>` | самопроверка: модули, типы, свойства и настройки стандартных реквизитов против XML-выгрузки той же конфигурации |

**Имена** выводятся в стиле XML-выгрузки: `Catalogs.Валюты.ObjectModule`, `Documents.ЗаказПокупателя.Forms.ФормаДокумента.FormModule`,
`Catalogs.X.Commands.Y.CommandModule`, `CommonModules.ОбщегоНазначения.Module`, `Configuration.SessionModule`. Виды модулей:
ObjectModule, ManagerModule, RecordSetModule, ValueManagerModule, CommandModule, FormModule, Module,
OrdinaryApplicationModule, ManagedApplicationModule, SessionModule, ExternalConnectionModule.
В запросах можно писать по-русски: `Справочник.Валюты.МодульОбъекта`, `ОбщийМодуль.ОбщегоНазначения`,
`Документ.X.Форма.ФормаДокумента`, `РегистрСведений.X.МодульМенеджера`.

**Как выбираются модули** по фильтру (`--path`, `modules`, `export`, `diff`). Сначала ищется точное имя модуля.
Затем имя объекта вместе с его формами и командами: `Документ.ЗаказПокупателя.Форма.ФормаСписка` — ровно эта форма,
без `ФормаСпискаПланшет`. Затем начало имени и, наконец, подстрока без учета регистра. `module <имя объекта>` выводит
только собственные модули объекта (`Справочник.Валюты` — модуль объекта и менеджера); если подошли модули разных
объектов, выводится список — уточни имя или добавь `--all`.

**Способ хранения модуля** (колонка в `modules`):
- с текстом: `text`, `plain text` (старый модуль без контейнера), `managed form`, `ordinary form`;
- без текста:
  - `image only` — поставка без исходников, есть только скомпилированный образ;
  - `encrypted` — модуль закрыт паролем;
  - `form without module` — у формы нет модуля;
  - `binary`, `container:…` — нераспознанное, стоит посмотреть `check` или `references/storage-format.md`.

Текста у таких модулей нет, так и скажи; скомпилированный образ скилл не разбирает.

**Типы в `fields`**:
- примитивные: `String(50)`, `String(10,Fixed)`, `String(unlimited)`, `Number(15,2)`, `Number(10,0,Nonnegative)`,
  `Date`/`DateTime`/`Time`, `Boolean`;
- ссылки и наборы: `CatalogRef.X`, `DocumentRef.X`, `EnumRef.X`, `ChartOfAccountsRef.X`, `TypeSet:DefinedType.X`,
  `TypeSet:Characteristic.X`, `TypeSet:CatalogRef` (любой справочник), `TypeSet:AnyIBRef` (любая ссылка);
- платформенные: `ValueStorage`, `UUID`.

Составной тип пишется через запятую, путь поля табличной части — `Товары.Номенклатура`.

**Стандартные реквизиты в `fields`** — вид `Standard`, имя по-русски и в скобках по-английски: `Код (Code)`,
`Регистратор (Recorder)`. `НомерСтроки` табличной части стоит перед ее реквизитами: `Товары.НомерСтроки (LineNumber)`.
Стандартные табличные части идут так же: `ВидыСубконто.ВидСубконто (ExtDimensionType)`,
`БазовыеВидыРасчета.ВидРасчета (CalculationType)`.
- Типов стандартных реквизитов в хранилище нет, платформа выводит их из свойств объекта, и скилл повторяет ее правила.
  Есть только применимые реквизиты:
  - `Родитель` — только у иерархического справочника, `ЭтоГруппа` — только при иерархии групп и элементов;
  - `Код`, `Наименование`, `Номер`, `Порядок` счета — только при ненулевой длине;
  - у регистра сведений `Период` — только у периодического: `DateTime` для периодичности «в пределах секунды» и
    «по позиции регистратора», иначе `Date`;
  - `Регистратор`, `НомерСтроки`, `Активность` — только у регистра, подчиненного регистратору;
  - `ВидДвижения` — только у регистра остатков и у некорреспондирующего регистра бухгалтерии, `Счет` — только у
    некорреспондирующего;
  - `Субконто1…N` и `ВидСубконто1…N` регистра бухгалтерии — по максимальному числу субконто плана счетов; тип
    `СубконтоN` — тип значения ПВХ видов субконто;
  - у ПВР `ПериодДействияБазовый` и `ВытесняющиеВидыРасчета` — только при использовании периода действия,
    `БазовыеВидыРасчета` — только при зависимости от видов расчета; `ВедущиеВидыРасчета.ВидРасчета` — все ПВР
    конфигурации;
  - у регистра расчета `БазовыйПериодНачало/Конец` — только при базовом периоде, `ПериодДействия…` — только при
    периоде действия;
  - `ВедущаяЗадача` бизнес-процесса — любая задача конфигурации; `БизнесПроцесс` и `ТочкаМаршрута` — только у задачи,
    которую использует бизнес-процесс.
- `Регистратор` — документы, в движениях которых есть регистр. `Ссылка` журнала — его документы, а `Номер` журнала —
  строка длины самого длинного строкового номера этих документов и (или) число длины самого длинного числового.
- В квадратных скобках — настройки, измененные в конфигураторе: `[Synonym=Артикул; FillChecking=ShowError]`. Это
  синоним, подсказка, комментарий, маска, проверка заполнения и «заполнять из значения заполнения».
- `(assumed)` — реквизит выведен из свойства, место которого для этой версии формата объекта не снято (как в `props`).
- Разбираются все классы со стандартными реквизитами: справочники, документы, перечисления, планы видов
  характеристик, счетов и видов расчета, планы обмена, бизнес-процессы, задачи, журналы документов, регистры
  сведений, накопления, бухгалтерии и расчета. У обработок и отчетов выводится `НомерСтроки` табличных частей.

**Свойства в `props`** называются и записываются как в XML-выгрузке: `InformationRegisterPeriodicity Day`,
`WriteMode RecorderSubordinate`, `Hierarchical true`, `RegisterRecords AccumulationRegisters.X, …`,
`Handler CommonModules.X.Процедура`, `Server true`, `ReturnValuesReuse DuringSession`. Всего 338 свойств в 43 классах.
Места свойств в описании объекта сняты сверкой с XML на семи конфигурациях отдельно для каждой версии формата
объекта: в одной конфигурации объекты бывают записаны разными поколениями платформы. Места 15 свойств, для которых
объектов не хватило (длины у плана счетов, корреспонденция, тип номера процесса и задачи…), сняты на тестовой
конфигурации с нарочно редкими значениями и лежат в `scripts/props_manual.json`.
- `(assumed)` — версия формата объекта в обучении не встречалась, значение взято с места, общего для всех известных
  версий. Обычно верно, но для важного вывода перепроверь.
- `?<код>` — код значения, которого не было в обучении.
- Свойства, которых нет в выводе, для этой версии формата не определены. Это не значит «пусто».
- Составные свойства:
  - `InputByString`, `DataLockFields` — поля объекта по порядку: `Description, Code, Артикул`. В `props.tsv` и для
    `usedby` они записаны полными путями (`Catalogs.X.Attributes.Артикул`, `Catalogs.X.StandardAttributes.Code`),
    поэтому `usedby "Справочник.X.Attributes.Артикул"` находит и их;
  - `Characteristics` — по одной на строку: `types <откуда виды>: key <поле>, filter <поле> = <значение> | values
    <где значения>: object <поле>, type <поле>, value <поле>`. Поля названы относительно своего источника.
    Значение отбора — предопределенный элемент (`Catalogs.НаборыДополнительныхРеквизитовИСведений.Справочник_Номенклатура`),
    `….EmptyRef` или строка в кавычках. Ссылка на удаленный предопределенный элемент выглядит как в XML:
    `<TypeId>.<uuid>`, удаленный источник — пустое место.
  - Сверено с XML на девяти конфигурациях и тестовой: все 9308 значений совпали (ввод по строке у 3270 объектов,
    поля блокировки у 73, характеристики у 723).

На конфигурациях, которые в обучении не участвовали, верны 99,9% значений свойств.

## Примеры

```bash
S="<скилл>/scripts/cfgread.py"
py -X utf8 "$S" sql:trade info
py -X utf8 "$S" --no-sync sql:trade module "Документ.ЗаказПокупателя.МодульОбъекта" --lines 1-80 2>/dev/null
py -X utf8 "$S" --no-sync sql:trade grep "ЦеныНоменклатуры" --proc --ctx 2
py -X utf8 "$S" "D:\Bases\Shop\1Cv8.cf" fields "Документ.РеализацияТоваровУслуг"
py -X utf8 "$S" "D:\Bases\Shop" grep "ПриЗаписи" --path "Документ.РеализацияТоваровУслуг" --proc
py -X utf8 "$S" "D:\Bases\Shop\1Cv8.cf" diff "D:\Bases\Shop"
py -X utf8 "$S" "D:\Incoming\client.cf" diff sql:trade --fields --props --show "*"
py -X utf8 "$S" --no-sync sql:trade usedby "РегистрНакопления.ТоварыНаСкладах"
py -X utf8 "$S" --no-sync sql:trade props "РегистрСведений" --prop InformationRegisterPeriodicity
py -X utf8 "$S" sql:trade export "D:\temp\trade-src"
```

`grep` и `modules` по всей большой конфигурации (УТ 3.1) идут около 10–13 с, потому что каждый раз извлекаются тексты
всех модулей. Для серии вопросов по одной базе один раз сделай `export` и дальше ищи по папке обычным Grep.

## Рецепт: где пишется регистр или используется объект

Сначала `usedby "РегистрСведений.X"`: он сразу покажет документы, в движениях которых есть регистр, подсистемы и
последовательности. Для общего модуля он покажет подписки на события и регламентные задания, которые его вызывают.
Затем ищи по голому имени объекта: `grep "ЦеныНоменклатуры" --proc`. Обращение `РегистрыСведений.X` есть не везде. В модулях
самого объекта (модуль менеджера, модуль набора записей) имя не повторяется: там стоит просто `СоздатьМенеджерЗаписи()`,
`СоздатьНаборЗаписей()` или `.Записать(`. Поэтому собственные модули объекта посмотри отдельно
(`modules "РегистрСведений.X"`, `module …`). Если запись идет через экспортную процедуру менеджера, найди ее вызовы
(`grep "X.<ИмяПроцедуры>("`). Учитывай `Движения.X` в документах и тексты запросов. Скилл не видит внешние обработки,
расширения базы и ручной ввод; если они могут писать в объект, скажи об этом.

## Что важно знать при ответах

- **Какая конфигурация читается.** Из SQL читается конфигурация базы данных — то, что применено к базе. Сохраненные в
  конфигураторе, но не примененные изменения (`info`: «ConfigSave rows» больше нуля) здесь не видны. Динамические
  обновления учитываются: у измененных файлов берется последняя копия `_dynupdate_`.
- **Файловая база** читается прямо из `1Cv8.1CD`, только на чтение; база может быть открыта в 1С. Если в этот момент
  конфигурацию обновляют, можно поймать ее на середине записи; тогда повтори чтение. Поддержан формат хранения 8.3.8
  (`info`: `storage format 8.3.8.0`); на старом формате 8.2.14 скрипт откажется с понятной ошибкой.
- **Расширения, установленные в базе, не читаются** (таблица ConfigCAS). `info` выводит их список или `none`; если
  расширение важно, читай его .cfe.
- **Заимствованный объект в .cfe** хранит только имя, ссылку на объект конфигурации и то, что добавило расширение:
  реквизиты, табличные части, формы, модули. Остальные его свойства там — значения по умолчанию.
  - `props` выводит у него `ObjectBelonging Adopted` и непустые списки с пометкой `(in extension)`; в списках только
    объекты, которые есть в расширении (у `Owners` может не хватать владельцев).
  - Стандартных реквизитов `fields` у него не выводит, кроме `НомерСтроки` табличных частей. Нет и типа самого объекта
    у заимствованного определяемого типа и ПВХ; у константы тип настоящий.
  - Длины кода, иерархию, владельцев и прочее смотри в основной конфигурации.
- **Современный .cf выглядит пустым для старых утилит.** Начиная примерно с режима совместимости 8.3.17 файл
  начинается с заглушки — «пустой конфигурации» `BB71D8BD57664101889B95C34FEA2351` с одним языком, — а настоящая
  конфигурация лежит дальше в 64-битном контейнере. Скилл читает ее (`info`: `file layout: 64-bit container`). Если
  другая утилита (v8unpack и т.п.) видит такую пустую конфигурацию, файл не испорчен.
- **Не ищи по сырым байтам .cf или кеша.** В старых контейнерах в свободных блоках остается удаленный код, а модули
  сжаты. Ищи через `grep` скилла или по папке `export`.
- **`Unknown:<uuid>` в типе** — ссылка на объект, которого в конфигурации больше нет (XML-выгрузка такие молча
  выбрасывает), или платформенный тип, которого нет в таблицах скилла.
- **Что не разбирается**:
  - свойства собственных полей: индексирование, проверка заполнения, параметры выбора;
  - предопределенные элементы, права ролей, разметка форм.

  За этим иди в XML-выгрузку (скиллы `meta-info`, `form-info`, `role-info`) или в конфигуратор.
- В ответе называй источник и его состояние: «база trade, кеш синхронизирован сейчас», «client.cf от 25.11».

## Если что-то не сходится

Если есть XML-выгрузка той же конфигурации (например, каталог Conf рядом с базой), `check <папка>` покажет,
совпадают ли модули, типы, свойства и настройки стандартных реквизитов. Ожидаемый результат:
- «module text equal» на все непустые модули и «non-empty modules in XML not matched: 0»;
- «type equal» на поля;
- для свойств — почти все «equal»;
- для настроек стандартных реквизитов — «equal». Изредка бывает «not in XML»: у старых объектов в XML-списке нет
  реквизита, который платформа все же создает (например, `ЭтотУзел` плана обмена).

Расхождения выводятся списком. Так стоит проверить первый запуск на
конфигурации нового поставщика или новой платформы. Устройство хранения, таблицы констант и как их дополнить — в
`references/storage-format.md`.
